# Privacy status

Hauntbox implements browser-encrypted submissions, public Ootle inclusion receipts, participant and host PIN/passkey authentication and native private testnet rewards. The full flow has passed against the isolated local chain. The production build runs locally with Esmeralda configuration and submissions, anchoring and payouts paused. Public Esmeralda proof and release review remain outstanding. `/demo` is explicitly simulated and moves no funds. There is no analytics or session replay, and fonts are served locally.

The intended live boundary is browser encryption for a specific curator, public fingerprints of encrypted bytes, and native stealth testnet rewards. The curator can decrypt on arrival. A selected reward discloses its recipient and amount to the operator wallet service. The operator controls testnet funds. Public fees, output keys, signatures, timing and transaction structure remain visible or inferable. A receipt establishes inclusion only, not authorship or payment; rewards are discretionary.

The browser uses RSA-OAEP-256/A256GCM JWE with a fixed 4,096-byte padded payload. Working curator keys are nonextractable CryptoKeys stored in the browser. Key recovery requires an encrypted export and a separate recovery code; recovery is exercised before room activation. Approved payout intents are encrypted at rest with a service key that the operator service can use. Public-network proof, retention policy and operational release controls remain pending. No anonymity, guaranteed reward, noncustodial service, timed decryption, or mainnet safety claim is made. An actively malicious operator could serve modified JavaScript, substitute an initially displayed room key, or disclose payout details; a compromised browser or curator could reveal content.

Participants create native Tari wallets on their own computers. Hauntbox accepts a receive address and does not collect wallet spending keys, seeds or wallet passkeys. Operator receipt and reward wallets have separate persistent state and unlock material. Wallet admin ports bind to loopback; public application routes do not forward wallet RPC. Exact-value secret scans and synthetic request checks are bounded evidence, not a general proof against all leakage. Preserve private backups of wallet state, matching unlock material, database state and separate curator recovery material. Do not fund the old authentication-disabled research wallets for public use.

Testnet application accounts support an 8–12 digit PIN with a separate random account sign-in code, or a passkey. The service stores salted PIN hashes, account-code hashes, passkey public keys and private session metadata; it does not store plaintext PINs. The payout address saved from account setup remains in this browser. Account sign-in does not create a wallet or authorize spending, and participant accounts cannot access the host inbox. This account layer adds identity/session metadata and does not establish anonymity. PIN endpoints reject mainnet; production security gates are recorded in docs/adr/003-sign-in-and-mainnet-security.md.

The new primary participant wallet flow generates native Ootle keys on the device. Its PIN is never sent to the API or stored as plaintext; wallet recovery material is encrypted in browser IndexedDB, wrapped with both a PIN-derived key and a nonextractable local device key. Its two Hauntbox recovery phrases are shown during setup and accepted by local recovery. They are not the native daemon's single seed phrase. Choosing the wallet reward address puts that address into the encrypted submission payload. Legacy app-account PIN hashes remain in the private database, under the secondary account/passkey option. Browser-held keys add a same-origin JavaScript/XSS custody boundary and are testnet only; no mainnet security claim is made. See docs/adr/004-browser-wallet-recovery.md.

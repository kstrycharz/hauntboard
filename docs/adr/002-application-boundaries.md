# ADR 002 — envelope, authority and payout boundaries

Date: October 2, 2026. Accepted for local application v1; public release remains gated.

Submission format is compact JWE using RSA-OAEP-256 with a 3,072-bit room key and A256GCM. Its protected header permits only alg, enc, typ, version, network, component, submissionId and keyThumbprint. Exact context values must match the verified room. Unknown headers, unsupported algorithms, wrong network/context and malformed segment sizes reject. The JSON story payload permits version, text, nickname and payoutAddress only. UTF-8 byte limits are 2,000/80/512; a four-byte big-endian JSON length and zero padding produce a fixed 4,096-byte encrypted payload. The digest hashes the exact compact envelope with the `hauntbox:envelope:v1:` prefix; changing any byte changes the inclusion proof.

The browser creates a room RSA key, exports a private JWK only into an established authenticated-encryption recovery file, and supplies a separately generated 256-bit recovery code. Restored working CryptoKeys are nonextractable and remain in browser IndexedDB. Before room creation the curator performs a real restore and decrypt roundtrip. The API receives the public RSA JWK and matching thumbprint, never the room private key. Browser code and the initial public-key display remain operator trust boundaries; on-chain immutability cannot make maliciously served JavaScript trustworthy.

HauntboxRoom binds its mutation authority to the creation transaction signer. Constructor parameters fix room ID, network, key fingerprint, policy digest and capacity; optional epoch closure is tested in the engine. Public reads return minimal room/receipt state. Receipt IDs and digests are immutable, and identical retry returns the original receipt. Close, capacity and exact closing-epoch rules reject new receipts. Application policy uses manual close; the template does not implement UTC deadlines, escrow or timed decryption. This version records public state rather than additional contract events.

The API cannot validate encrypted story semantics. It validates exact envelope shape, context, digest, challenge, capacity and idempotency; ciphertext storage and a single outbox job commit together. Lookup authorization is a separate 256-bit capability presented in an Authorization header and stored hashed. Public receipts contain inclusion fields only. A confirmed receipt requires the expected accepted transaction and independently verified component/effect, not HTTP success alone.

A curator intentionally discloses one opened recipient and exact integer amount to request a short-lived payout quote. The server encrypts the bound intent with its private service key. Fresh passkey-backed authorization and CSRF checks protect confirmation; unique database constraints and advisory locks prevent duplicate jobs. The worker reserves fees and daily reward allowance before one signing call. A lost response freezes unknown with its reservation intact, and restart reconciles a known transaction ID without another signing call. Native Tari constructs the concealed transfer; the app does not implement wallet cryptography. Fees and transaction structure remain visible.

Participant wallet keys belong to the native wallet on the participant's computer. Operator receipt and reward wallets remain separate. Mainnet is rejected by the current app configuration; a future mainnet treasury/custody design needs its own authorization and review.

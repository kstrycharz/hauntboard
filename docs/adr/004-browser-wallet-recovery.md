# Browser-held participant wallet — testnet

October 2, 2026. The user requested prominent popup account creation, a PIN keypad, real wallet generation, recovery material shown once and phrase-based recovery. This supersedes ADR 003's existing-wallet-only participant path. Host/operator identity and native host wallet service isolation remain as documented in ADR 003.

The main account page now offers Create wallet and Recover wallet. Create opens a native modal dialog, chooses and confirms an 8–12 digit PIN, generates native Ootle owner/view keys in the browser, displays recovery material once, asks for a saved-word confirmation and persists the encrypted wallet. The wallet is then unlocked for choosing the submission's reward address. Reload/remount locks it. Recovery imports both phrases, chooses a new local PIN and restores the same network address. Creation, recovery and unlock use one network-scoped same-origin Web Lock. Recovery checks the current persisted address while holding that lock and rejects replacement by a different wallet. BroadcastChannel updates refresh and lock other tabs; the originating tab ignores its own notification. Browsers without Web Locks fail closed.

## Native key and recovery format

`@tari-project/ootle-wasm` is pinned to 0.43.0, matching the selected native engine/wallet release. `generateOotleSecretKey`, `ootlePublicKeyFromSecretKey` and `generateOotleAddress` perform the native operations. No Ristretto scalar arithmetic or wallet key derivation is handwritten in JavaScript. The address contains native owner and view public keys for the selected network.

This released WASM API restores raw owner/view keys but does not expose the daemon's cipher-seed mnemonic derivation. Hauntbox uses `@scure/bip39` 2.0.1's established checksum encoding to represent each native 32-byte key as a 24-word phrase: one spending phrase and one view phrase. Both are required. These are explicitly labelled Hauntbox recovery phrases, not a native Tari daemon seed phrase. They reconstruct the exact generated keys and address; they do not promise compatibility with a daemon's single-seed import UI. A separately verified official cipher-seed browser adapter is required before offering native single-seed import. No arbitrary native seed input is silently accepted as a Hauntbox phrase.

Official source references: [released WASM key bindings](https://github.com/tari-project/tari-ootle/tree/v0.43.0/bindings), [Ootle TypeScript SDK](https://github.com/tari-project/ootle.ts), [scure BIP39 implementation](https://github.com/paulmillr/scure-bip39). Package versions and integrity are recorded in pnpm-lock.yaml.

## Local storage and authentication

The new wallet PIN and both phrases never enter a server request. The PIN itself is not persisted. Browser IndexedDB contains an AES-GCM encrypted recovery payload, salt/IVs, a public receive address, local attempt state and a nonextractable device AES key. A PBKDF2-SHA256 key with 600,000 iterations encrypts the payload using the PIN. A second AES-GCM layer uses the nonextractable device key. Both layers authenticate a version/network/address context. Device loss requires both recovery phrases; a ciphertext export without its original device key cannot restore this wallet.

Five failed local PIN decryptions trigger a 15-minute local lock that survives reload. Attempts are serialized across tabs; only rejected PIN decryptions count. SDK loading, storage failures and invalid outer wallet data produce separate actionable errors without consuming a failed-PIN allowance. A cancelled operation before recording its outcome does not count. This is a convenience control, not a tamper-resistant hardware counter: the browser owner or malicious same-origin code can manipulate browser storage or invoke its keys. A short PIN, nonextractable WebCrypto key and local attempt limits do not establish mainnet custody security. JavaScript strings cannot be reliably zeroized; temporary recovery/PIN form state is removed on finish/cancel, byte buffers are wiped where possible, and the SDK's key objects are freed.

Unlock decrypts the wallet and re-derives its address before accepting it. It does not grant a host session, native daemon permission or spending permission to the API. The original database-backed participant app accounts remain under Existing app account / passkey sign-in for compatibility. Their PIN hashes remain server-side as ADR 003 describes. The new browser wallet and those old account credentials are distinct; no automatic migration or invented identity link occurs.

## Boundaries and remaining work

The wallet generation, PIN unlock, recovery and payout-address selection are implemented for localnet and Esmeralda. Mainnet fails closed. No wallet seed is retained by the API, and there is no new public faucet, deposit, signing or transaction endpoint. Browser balance scanning and outgoing spending, independently confirmed receiving/spending from this new browser implementation, native cipher-seed import and passkey PRF wrapping of browser wallet keys remain work packages. Existing passkeys authenticate application accounts; they do not yet unlock this browser wallet's keys. The prior native daemon private-reward flow remains separately verified.

Before mainnet: use reviewed entropy/key wrapping and stronger authentication than a PIN-only browser session, explicitly detect passkey PRF support and define a supported recovery alternative, review secret exposure/XSS/dependencies, prove native recovery and real recipient spending, and complete the independent custody/operations gates in ADR 003. Reuse neither testnet seeds nor faucet wallets for mainnet.

## Evidence

Chromium and Firefox passed actual UI wallet generation, keypad/modal behavior, encrypted IndexedDB storage with a nonextractable device key, no PIN/phrase POST requests, PIN unlock after reload, local lockout after failed attempts, clean-browser recovery to the identical address and address selection in the submission form. Production-build tests also passed through Caddy with the actual WASM content-security policy. These tests make no chain transactions or faucet claims. Sanitized records are docs/evidence/m2/embedded-wallet.json and embedded-wallet-production.json; fixture seeds stay in the private local CI volume and are included in bounded exact-value leakage checks.

## Code review — October 2, 2026

Static review of commit `6dee866` found the following issues. The table preserves the original findings and acceptance criteria. **BW-01, BW-02 and BW-03 are now closed** by the October 2 implementation and Chromium/Firefox regression evidence in docs/evidence/m2/wallet-concurrency.json. The original review itself was static; the subsequent correction was tested at runtime.

| ID | Priority | Finding and impact | Required correction | Acceptance evidence |
| --- | --- | --- | --- | --- |
| BW-01 | P1 | `saveWallet` checks existence before asynchronous crypto and later unconditionally replaces the record. Two tabs can both report successful creation although only the last wallet survives. Recovery's address check uses potentially stale React state. A displayed reward address can therefore differ from the persisted wallet. | Make creation and recovery atomic across tabs. Recheck existence/address against the current persisted record at commit; reject conflicting creation or replacement and refresh the affected UI. | Two tabs sharing one browser profile race to create distinct wallets: exactly one succeeds and storage matches that winner. A recovery tab opened before another tab creates a different wallet must reject replacement and preserve the existing wallet. |
| BW-02 | P2 | `unlockWallet` separately reads and writes the entire record. Parallel attempts can lose failure increments; a successful unlock can write stale encrypted data back after another tab changes the PIN through recovery. | Serialize operations across tabs, preserve record versions, and update attempt state without overwriting newer wallet ciphertext or credentials. Coordinate with BW-01. | Concurrent failed unlocks enforce the intended count. A recovery/PIN change racing an old unlock must retain the new PIN and ciphertext; an old operation must not roll them back. Verify sequential reload lockout still works. |
| BW-03 | P2 | The unlock catch block labels SDK loading, address reconstruction and storage-write errors as `WALLET_PIN_INCORRECT`. Attempts are already counted, so a correct PIN during an infrastructure failure can lead to misleading retries and lockout. | Separate authentication/decryption failures from unavailable storage, invalid wallet data and unavailable SDK code. Preserve appropriate failure counting without penalizing known non-authentication failures; return actionable safe messages. | Inject SDK-loading and storage-write failures with a correct PIN: neither is reported as an incorrect PIN or consumes a failed-PIN allowance. Incorrect PINs still count and lock as intended. Corrupted data produces a recovery-oriented error without exposing secrets. |

Relevant code: `apps/web/src/participant-wallet.ts` (`saveWallet` and `unlockWallet`), `apps/web/src/EmbeddedWallet.tsx` (cross-tab refresh and safe errors), and `apps/web/src/browser-vault.ts` (synchronous IndexedDB errors and aborted transactions now reject instead of hanging). Regression command: `docker compose -f compose.app.yaml -f compose.app.localnet.yaml -f compose.app.browser.yaml run --rm --no-deps browser-tests node scripts/test-wallet-concurrency.mjs`. Both browsers proved one creation winner, conflicting recovery preservation, shared failure counts, PIN-rotation integrity, correct-PIN SDK/storage failure classification and damaged outer ciphertext recovery. The existing sequential UI suite passed again. No faucet or chain operation was made by these tests. These fixes do not remove the separate mainnet and native recovery compatibility gates.

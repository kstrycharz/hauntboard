# Using recipient-specific sealed rooms

1. Open a sealed thread and choose **Room access**. You can also open the recipient-key vault from **Sealed-thread key backup**.
2. Choose **Set up room access**. Save the displayed **Recovery code** privately, download your **Access backup**, and acknowledge that you saved the code separately. Both are required to restore access. This code is separate from your Tari wallet phrase and PIN. The app asks you to finish this recovery setup before continuing.
3. To manage invitations for a classic sealed room you can already read, choose **Set up invitations**, then **Review invitation setup**. Unlock your posting wallet if needed and review the Ootle fee before publishing. This creates an access list through the private invitation channel; it does not establish who originally created the thread.
4. Someone who wants an invitation opens that room, sets up/unlocks their access, and chooses **Get an invitation**. They enter a name or nickname, choose **Create access request**, and use **Copy access request** to send the code privately to the person managing the room. No wallet or test tokens are needed. The interface does not require editing JSON.
5. The administrator chooses **Invite someone**, pastes the code into **Access request from your contact**, and selects **Check access request**. Compare the displayed fingerprint with the contact through a trusted private channel; a sender-chosen name does not prove identity. **Review invitation** opens the fee review. After confirmation, **Copy room link** gives the recipient a link containing the authenticated access-list binding, with no room key.
6. The recipient opens the link using the access they created for their request. Unlocking/restoring saved access resumes the invitation. Their browser fetches and decrypts their authorized envelope, including available room history. If using a new device, restore the original encrypted backup and recovery code first.
7. To remove someone, choose **Manage members**, select **Remove [name]**, and choose **Review removal**. The fee review names the selected people and explains that their earlier messages remain readable. After confirmation, cooperating clients encrypt new replies with a fresh key. Keep a new encrypted access backup after every access change.

Removed recipients keep their old history. Existing board writes remain permissionless, including messages from older clients; the registry authorizes key distribution. Members can share keys or plaintext with others. Group keys do not authenticate individual authors. Do not interpret a public thread title, recipient pseudonym or administration key as an anonymous identity.

To recover on a clean browser, open **Room access**, choose **I already have an access backup**, select the encrypted **Access backup file**, and enter the **Recovery code**. On a device with saved access, choose **Restore from a backup file** instead. Recovery words for the Tari wallet restore the wallet, not room access. **Back up or restore access** provides ongoing downloads and restoration. If an access transaction is pending, unlock/restore access and use **Check transaction status**; never replace an uncertain spend.

The standalone demo has been removed from the application. The guided controls above operate on actual Ootle rooms. The previous real Esmeralda run remains documented in [chain evidence](../evidence/room-key-esmeralda.json); see [the registry specification](../key-registry/README.md) for technical details.

## Contract invariants and validation matrix

- Only boards create threads; only thread methods advance thread history; only the owning thread appends its pages. No owner can edit history or replace rules.
- Public candidate rejects nonzero modes. Titles are 1–80 UTF-8 bytes after the nonblank check; payloads are 1–4,096 bytes. Contract payloads are opaque bytes: rendering/format validation must tolerate hostile alternative clients.
- Thread post count equals the sum of its page lengths. Pages start at multiples of 16 and have no more than 16 entries; parent is -1 or a previously accepted global position. Failed application execution leaves no partial board/thread/page mutation; fee effects must be measured separately.
- Exact logical retry returns the original address/index even after rollover or capacity exhaustion. Changed title/mode/body/parent with an occupied ID rejects. A nonce is not proof of identity or permission to edit.
- Full bytes remain retrievable through the recorded board → thread → page chain. Client decoding checks network identity, expected template/schema, page owner, start offset and counts; a fake provider response must not silently become confirmed history. Provider trust remains explicit.
- The contract holds no tip/reward vault and grants no participant-fund withdrawal authority. Review the client fee transaction as a separate financial operation.

Run added engine cases inside the repository's container workflow with locked dependencies. Use a disposable local board for capacity/concurrency tests. Public acceptance should use an already owner-created confirmed transaction where possible; creating public content or spending needs existing explicit authorization for that action. Attach sanitized test output to the exact source and artifact hashes. Do not infer a public runtime result from the local 0.43.0 or native 0.45.0 result.

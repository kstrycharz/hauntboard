# Faucet funds, first thread and zero available for replies

Date: November 6, 2026

The clarified report is **receive 100 test TARI, publish a main thread, then see zero available when replying**. It is different from the fresh-wallet funding and faucet-receipt issues covered in the [earlier repair](reply-zero-balance-fix.md).

## Reproduced cause

The browser wallet spends a funding output and creates an owned change output. The posting fee is the calculated amount within the disclosed 1-test-TARI ceiling; the rest is change, not an additional posting charge.

Older wallets default to holding that change aside to reduce links between posts. Their total can therefore remain near 100 test TARI while their posting-ready balance becomes zero after the first thread. New wallets already use Standard posting, which permits verified, unreserved change to fund replies and later threads. Explicit isolation choices are retained.

There was also a UI timing gap: confirmation refreshed the wallet balance while posting-status rendering was paused. The next composer could retain its earlier readiness guidance until another balance refresh or failed posting attempt. The clarified sequence now has a dedicated regression rather than relying on an empty-wallet fixture.

This reproduces the reported symptoms from application behavior. The affected user's private wallet and exact transaction were not accessed.

## Repair

- After a confirmed thread, the reply composer immediately receives the latest funding guidance.
- A held balance is presented as, for example, **99 test TARI remaining · held by posting setting**, with an explanation of why it is held. It is not presented as an empty wallet needing another faucet payment.
- The primary action becomes **Use remaining tokens and reply** (or **Use remaining tokens and post**). Its adjacent disclosure explains that this enables Standard posting, can link posts through network activity and publishes the current draft.
- One click on that explicit action saves the setting, refreshes verified funds, checks the posting fee and submits the draft. The ordinary action remains Reply/Post when funds are ready. Hauntboard does not open a wallet review popup for the browser-wallet path.
- A separate **Enable remaining tokens without replying/posting** action preserves the ability to change the setting without publishing.
- Existing pending-operation checks, fee limits, input reservations and exact signed-envelope reconciliation still apply. Rendering a balance or editing a draft does not silently change the user's setting.
- Wallet output details now describe change as available when Standard posting is enabled, rather than always saying it is held separately.

The user should keep using the original funded wallet. Creating a second wallet does not move the remaining tokens and is unnecessary for this recovery.

## Verification scope

The focused native SDK test decrypts the actual change generated by the signed posting-fee program, checks its amount and posting-change memo, and verifies ownership in the original wallet.

The Chromium/Firefox native-wallet regression starts empty, imports a synthetic 100-token faucet payment, signs a thread, and uses the actual change commitment contained in that exact signed envelope. It reproduces zero posting-ready funds under isolation, explicitly enables Standard posting, reloads the encrypted wallet, and signs a real reply instruction spending that change. It also checks pending-input protection and restoration of change provenance after rejection.

The application GUI regression covers 100 tokens to a confirmed main thread to 99 held tokens to an explicit successful reply. It checks the remaining amount, policy disclosure, absence of another faucet claim or wallet popup, exactly one reply submission, and the ordinary Reply label afterward. Existing separate setting-only recovery still preserves the unsubmitted draft.

Provider acceptance, faucet funding and receipts are simulated in these regressions. Native crypto, fee construction, local storage and signing use the released SDK/WASM. These tests do not claim a new funded public-chain execution. Deployment validation checks public readiness and served assets without requesting tokens or publishing content.

Before release, all nine focused Node tests passed, as did 18 GUI scenarios per browser and the native wallet regression in both Chromium and Firefox. Release artifact checksums, bundled WASM and the published board identity also passed verification.

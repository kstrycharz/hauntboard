# Paged on-chain conversations

Schema 3 keeps the board registry (maximum 128 threads), thread metadata and post pages in separate components of the same published Hauntboard template. A thread stores its board, title, mode, 16-byte UID, page addresses and total post count. It stores no payloads. Each page stores up to 16 complete post envelopes, its owning thread address and its starting global index. A thread supports 128 pages, or 2,048 posts including the opening post. Each envelope is 1–4,096 bytes.

The BOR state tuple is `(schema, is_board, board, title, mode, uid, threads, posts, pages, post_count, page_owner, page_start)`. Boards have no pages or posts. Threads have no inline posts and an empty page owner. Pages have an owning thread, no page references and a local count. Strings represent component addresses to preserve compatibility with the tested 0.43.0 BOR boundary. Parent `-1` represents an opening or unattached post; other parents are earlier global indices in the same thread.

`create_thread(title, mode, uid, payload)` atomically creates the thread, opening page and registry entry. `append(nonce, parent, payload)` atomically appends to the current page or creates the next one. Global post indices never change; a reference to post 16 remains post 16 after rollover. All payloads remain in current chain state. This is partitioned storage, without deleting, summarizing or compressing history.

Page writes use the immutable `caller_component(thread_address)` access rule on `page_append`. No owner can change the rules. A direct signed transaction cannot write to a page, and calling the public thread `append` method on a page is rejected. The engine supplies author public keys from the transaction signer; clients cannot impersonate another author by passing a string.

A reply's 16-byte logical nonce has a four-byte little-endian page number followed by 12 cryptographically random bytes. The opening post uses its thread UID. This format allows exact retry checks against one bounded page, including after rollover. Identical signer/nonce/parent/payload retries return the original global index. Conflicting content or parent reuse fails. A fresh nonce targeting a previous page fails; a client must refresh the thread and review a new transaction. The nonce prefix is part of the authenticated encryption context. AES-GCM has a separate random 96-bit IV; its existing encryption scheme is unchanged.

Wallet transactions declare the thread and the nonce's existing page as inputs. Companion manifest transactions add explicit page reads because their input discovery cannot infer component addresses stored as strings. Browser transactions declare those inputs directly. Retrying thread creation also declares the existing thread and first page. A rollover creates its new page inside the transaction.

`GET /api/thread?address=...` returns metadata, the opening post and the newest two pages. `before=<global index>` retrieves earlier pages. The client pins the opening post, displays replies newest first and merges older replies by global index without duplicates. Each fetched page must be verified and match the configured template, thread owner, board, UID, mode and page offset. Page results are bounded by the thread's observed total count.

The schema-3 deployment has its own `/private/hauntboard-bootstrap-v3.json` journal. It preserves the schema-2 board and wallet data, adds the previous board/template to a compatibility allowlist, and exposes previous boards through the board chooser. Existing schema-2 threads retain their original immutable code and 32-post limit. Their addresses and invitations continue to work. No browser storage reset is part of this upgrade.

Validation: native engine tests exercise all 2,048 positions with maximum-size reply payloads, final capacity rejection, old-page retries, full-byte retrieval, invalid parents, identity conflicts and direct-page-write rejection. The live localnet paging test creates public and sealed conversations with 36 posts each, uses both signing paths across page boundaries, verifies three page components through the independent indexer, checks cross-page parents, retries, history loading and recovery after a browser reload. The PoC remains one isolated local validator; no public-network throughput or fee guarantees follow from these tests.

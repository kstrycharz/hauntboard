02 / TRY THE ACTUAL ROOM CONTROLS

Make access changes visible.

  1. Open a sealed conversation

    Choose Room access. Set up access, save the separate recovery code, and download the encrypted backup. Reading and requesting an invitation need no funded wallet.

  2. Invite another browser

    On the reader's device, create an access request and send it through a trusted private channel. The room administrator checks the request, reviews the fee, and publishes the invitation.

  3. Remove, rotate, compare

    After both readers can open a message, remove the invited reader in Manage members. Review the fee and wait for confirmation before posting a new message. The remaining reader can open it; the removed reader's old key cannot. Download a fresh backup after access changes.

Publishing posts, invitations and rotations costs test currency and requires a funded browser wallet. A full walkthrough can take longer than three minutes because confirmation and indexing take time.

    04 / WHY TARI?

    Separate the privacy layers.

    Native posting fees

    Tari stealth outputs and one-time authorization let the client pay posting fees without attaching its persistent wallet owner key or calling its named account. The board contract stores no author field. Funding history, fees and timing can still link activity.

    Room access on chain

    A companion Tari contract authorizes recipient-envelope grants and key rotation. AES-GCM message encryption and recipient encryption happen in the browser. The contract checks authority and revisions; it does not prove that an envelope was encrypted correctly.

    05 / EVIDENCE AND LIMITS

    Know what each check proves.

    • The recorded eight-transaction run covers recipient delivery, outsider rejection, encrypted recovery and future-message exclusion. It is dated October 21, 2026 UTC.
    • Native engine tests check contract authority and state transitions. Browser checks exercise encryption, recovery and interface behavior. Some browser transport is simulated; these layers are not interchangeable.
    • The separate same-wallet public posting audit remains incomplete. Different signers do not prove unlinkability. No anonymity claim is made.
    • Titles, categories, recipient pseudonyms, administration linkage, output ancestry, fees, timing and network activity can remain visible. This client trusts provider verification flags rather than independently verifying consensus.
    • Testnet resets or indexer retention can remove access to old records. A saved evidence file is not a substitute for a currently available chain receipt.
